# tdx-local-data-toolkit

三个纯标准库的小工具，用来回答本地通达信（TDX）vipdoc 数据的三类日常问题：

1. **这份 .day / .lc1 文件到底怎么解的？** —— `tdx_fmt.py`：按字节解析日线与 1 分钟线，
   并把结果按可复核的方式打印出来（含 JSON）。
2. **我本地的数据到底更到哪天了，有多少只没更新？** —— `audit_coverage.py`：
   按"末条记录的日期"算全库覆盖率，给出各市场分项 + 缺口文件清单。
3. **某天是不是交易日？** —— `check_trade_day.py`：周末 + 节假日表，
   表覆盖不到就明确说"未知"，而不是猜一个。

外加 `sample_builder.py`（造合成样本）和 `tests/run_selftest.py`（一键自测 59 项），
让**没有安装通达信、也没有任何行情数据的机器**也能完整验证解析逻辑。

零网络、零第三方依赖、对 vipdoc 只读。字节级格式说明与实测核验见 [FORMAT.md](FORMAT.md)。

> **非官方**：本工具与通达信（TDX）软件及其厂商无关；格式结论全部来自**本地文件实测**（未使用官方文档或源码）。
> **实测环境**：通达信 Windows 版 **V7.72**（2026-09）。不同版本可能不一致，每条结论都附了复核方法。
> **边界**：只处理**盘后**本地数据（**非实时**）；且**不做复权** —— `.day` / `.lc1` 为不复权原始值，
> 除权日直接比较价格会失真。

## 快速开始

    # 1) 不需要任何数据：先跑自测，确认解析逻辑在你的 Python 上正确
    python tests/run_selftest.py

    # 2) 解析一个真实文件（解析器只读，不改动任何东西）
    python tdx_fmt.py --info  <vipdoc>/sh/lday/sh600000.day
    python tdx_fmt.py --day   <vipdoc>/sh/lday/sh600000.day --last 5
    python tdx_fmt.py --lc1   <vipdoc>/sz/minline/sz000001.lc1 --last 5
    python tdx_fmt.py --lc1   <vipdoc>/sz/minline/sz000001.lc1 --last 5 --json

    # 3) 全库覆盖率审计（末条记录日期 == 目标日期 算命中）
    python audit_coverage.py --dir <vipdoc> --date 20260928
    python audit_coverage.py --dir <vipdoc> --date 20260928 --json out.json

    # 4) 交易日判断
    python check_trade_day.py                 # 今天
    python check_trade_day.py 20260928        # 指定日期
    python check_trade_day.py --list 2025     # 某年确认交易日清单
    python check_trade_day.py --verify-holidays <指数1.day> <指数2.day> <指数3.day>

把 `<vipdoc>` 换成你自己的 `vipdoc` 目录（其下有 `sh/sz/bj` 等市场子目录，
再下面是 `lday` / `minline`）。

## 覆盖率审计长什么样

`audit_coverage.py` 的口径只有一种：**读每个文件最后一条记录的日期**，
等于目标日期才算命中。为什么不用文件 mtime：批量刷新、盘后下载、复制目录都会改 mtime，
"mtime 是今天"既不保证有今天的数据，也不排除数据是旧的。

输出形状（示例，数值随机器而变）：

    目标日期 20260928 ｜ 扫描目录 vipdoc ｜ 文件总数 19253
      bj/day     349/352 = 99.1%
      bj/lc1     352/353 = 99.7%
      sh/day     4809/4877 = 98.6%
      sh/lc1     4830/4882 = 98.9%
      sz/day     4324/4381 = 98.7%
      sz/lc1     4340/4408 = 98.5%
      总覆盖率 = 19004/19253 = 98.7%
      缺口文件 249 个（末条日期 != 目标日期）：
        bj\lday\bj810011.day  末条日期=20260407
        ...

清单里的路径一律相对于 `--dir`，JSON 里也只记目录名不记绝对路径，方便直接贴进 issue。

**先在校准数据上确认它没写死**：`sample_builder.py` 造的样本里，10 个文件恰好 6 个命中，
审计必须报 **60.0%**；而且四个分组 `sh|sz / day|lc1` 的分项分别是 66.7%、66.7%、50.0%、50.0%
——不等才是对的，说明它是真算出来的。这条是自测里的硬断言。

## 交易日判断的"三档"设计

返回值不是布尔值，别把"未知"当"是"：

| 结论 | 含义 | 退出码 |
|:----|:-----|:-----:|
| 交易日 | 确认开市（周末规则排除、节假日表未命中，且在表覆盖范围内） | 0 |
| 非交易日 | 确认休市（周末，或命中节假日表） | 1 |
| 未知 | 该年份没有表 / 超出表覆盖范围 -> **必须自己核对交易所公告** | 3 |

内置表来自"多个指数日线文件里工作日的整体缺失"反推（不是手抄），
**2026 年只覆盖到 2026-09-28**，这之后的日期（含国庆长假）一律返回"未知"。
想复核：`--verify-holidays` 传你自己的指数日线文件，工具会打印每份文件相对并集缺多少天，
再与内置表逐日比对（PASS / DELTA）。注意**至少传 2~3 份文件**：实测单个指数文件自身有
4 个真实空洞，只用一个文件会把它们误判成休市日。

## 自测覆盖了什么

    python tests/run_selftest.py

59 项断言，全部真实执行，包含几项"故意坏掉"的用例：

- 日期字位解码 + 编码往返（含 2026-01-01 / 12-31 / 2032-02-29 等边界），并断言
  `v % 100` 的错误写法会解出不存在的日期；
- 解析器读回来的值 == 生成器写进去的值（往返一致，含 float32 容差）；
- 覆盖率审计必须**恰好** 60.0%（不是四舍五入来的近似值），缺口清单恰好 4 个文件；
- 交易日判断回归：含"单文件空洞被误判成节假日"这个坑（20260617 / 20260625 必须是交易日），
  以及"表覆盖不到时必须是未知"，以及 `--list 2025` 必须是 243 天；
- 合理性闸门：把 `.lc1` 当 `.day` 解、把 `.day` 当 `.lc1` 解、非法目标日期（20260984）、
  目录不存在、目录里没有目标类型文件 —— 全部必须当场 `SANITY_FAIL`，不许悄悄输出假结果。

自测在系统临时目录里建工作目录，不写进工具包，也不碰任何真实 vipdoc。

## 依赖与边界

- 只用标准库：`os` / `sys` / `struct` / `argparse` / `json` / `datetime`。Python 3.8+。
- 三个分析脚本对 vipdoc **只读**：只读打开、不写入、不改名、不删除；零网络。
- 只是**数据格式与本地数据完整性**工具：不产生买卖信号，不构成任何投资建议。
- `sample_builder.py` 造的是**合成数据**（确定性递推的假数值），不是任何真实标的或行情，
  只用于自测，不要当行情数据使用。
- 格式结论都写了复核方法；凡实测无法确认的（例如 `.day` 第 8 个字段的含义）都注明"未确认"，
  不编解释。
